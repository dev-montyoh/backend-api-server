# Feature Specification: 공개 회원가입 (Public User Registration)

**Service Module**: `user`

**Feature Branch**: `002-user-signup`

**Created**: 2026-07-22

**Status**: Draft

**Input**: baseline([001-user-service](../001-user-service/spec.md))에서 "범위 밖/미구현"으로 표시했던 공개 회원가입을 정방향 SDD로 신규 명세.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신규 사용자 회원가입 (Priority: P1)

계정이 없는 방문자가 로그인 아이디와 비밀번호를 제출하면 계정이 생성되고, 이후 그 자격증명으로 로그인할 수 있다.

**Why this priority**: 현재 계정 생성 경로가 운영자용 부트스트랩 어드민뿐이라, 일반 사용자가 서비스에 진입할 방법이 없다. 회원가입은 사용자 유입의 전제 조건이다.

**Independent Test**: 아직 존재하지 않는 아이디로 회원가입을 요청해 계정이 생성되는지, 그리고 같은 자격증명으로 로그인이 성공하는지로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 미사용 로그인 아이디와 정책을 만족하는 비밀번호, **When** 회원가입을 요청하면, **Then** 계정이 생성되고 성공 응답을 받는다.
2. **Given** 방금 가입한 자격증명, **When** 로그인을 시도하면, **Then** 로그인에 성공하고 토큰을 발급받는다.
3. **Given** 회원가입 성공, **When** 응답을 확인하면, **Then** 응답 어디에도 비밀번호(평문/해시)가 포함되지 않는다.

---

### User Story 2 - 중복 아이디 방지 (Priority: P1)

이미 사용 중인 로그인 아이디로는 가입할 수 없어야 한다.

**Why this priority**: 로그인 아이디가 계정 식별자이므로 중복은 인증 무결성을 깨뜨린다. US1과 사실상 한 쌍이다.

**Independent Test**: 존재하는 아이디로 가입을 재시도해 거부되는지, 기존 계정이 영향받지 않는지로 검증.

**Acceptance Scenarios**:

1. **Given** 이미 존재하는 로그인 아이디, **When** 같은 아이디로 회원가입을 요청하면, **Then** 중복을 알리는 명확한 오류를 반환하고 새 계정을 만들지 않는다.
2. **Given** 중복으로 가입이 거부됨, **When** 기존 계정 상태를 확인하면, **Then** 기존 계정의 자격증명은 변경되지 않는다.

---

### User Story 3 - 입력 검증 (Priority: P2)

형식에 맞지 않는 입력(빈 값, 너무 짧은 비밀번호 등)은 계정을 만들지 않고 거부한다.

**Why this priority**: 잘못된 계정 데이터가 저장되는 것을 막고, 사용자에게 무엇이 잘못됐는지 알려준다. 핵심 흐름은 아니지만 데이터 품질과 UX에 필요.

**Independent Test**: 빈 아이디/짧은 비밀번호 등으로 요청해 각각 거부되고 계정이 생성되지 않는지 검증.

**Acceptance Scenarios**:

1. **Given** 빈 로그인 아이디 또는 빈 비밀번호, **When** 회원가입을 요청하면, **Then** 검증 실패 오류를 반환하고 계정을 만들지 않는다.
2. **Given** 정책 최소 길이에 못 미치는 비밀번호, **When** 회원가입을 요청하면, **Then** 검증 실패 오류를 반환한다.

### Edge Cases

- 동일 아이디로 거의 동시에 두 요청이 들어오면? → 최종적으로 계정은 1개만 존재해야 한다(중복 생성 금지).
- 회원가입 처리 중 저장 실패 시 부분 생성이 남지 않아야 한다.
- 비밀번호는 어떤 로그(성공/실패 로그 포함)에도 평문으로 남기지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 방문자가 로그인 아이디와 비밀번호를 제출해 새 계정을 생성할 수 있는 **공개(인증 불필요) 회원가입 경로**를 제공해야 한다.
- **FR-002**: 시스템은 로그인 아이디의 유일성을 보장해야 하며, 이미 사용 중이면 계정을 만들지 않고 중복 오류를 반환해야 한다.
- **FR-003**: 시스템은 비밀번호를 복원 불가능한 해시 형태로만 저장해야 하며, 어떤 응답·로그에도 평문/해시를 노출하지 않아야 한다.
- **FR-004**: 시스템은 회원가입 입력을 검증해야 한다 — 로그인 아이디·비밀번호는 비어 있을 수 없고, 비밀번호는 최소 길이 정책을 만족해야 한다.
- **FR-005**: 회원가입에 성공한 사용자는 추가 활성화 단계 없이 즉시 로그인할 수 있어야 한다.
- **FR-006**: 시스템은 각 계정에 대해 고유한 내부 사용자 식별자를 부여해야 한다(로그인 아이디와 별개).
- **FR-007**: 회원가입 성공 응답은 계정이 생성됐음을 명확히 나타내야 한다(민감정보 없이).

*비밀번호 정책 기본값 (합리적 기본 — Assumptions 참조):* 최소 8자. 별도 요구 없으면 이 값을 채택.

### Key Entities

- **User**: 계정. 로그인 아이디(고유), 해시된 비밀번호, 로그인 아이디와 분리된 고유 내부 식별자를 가진다. baseline [001-user-service](../001-user-service/spec.md)의 User 애그리게잇을 **재사용**한다(신규 엔티티 아님).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신규 방문자가 회원가입 후 곧바로 로그인까지 성공하는 전체 흐름이 동작한다(정상 경로 성공률 100%).
- **SC-002**: 이미 존재하는 아이디로의 가입 시도는 100% 거부되며, 중복 계정이 0건 생성된다.
- **SC-003**: 유효하지 않은 입력(빈 값/짧은 비밀번호)은 계정을 생성하지 않고 거부된다.
- **SC-004**: 어떤 응답이나 로그에서도 비밀번호가 노출되지 않는다(0건).
- **SC-005**: 동일 아이디 동시 요청 시에도 최종 계정 수는 1개다.

## Assumptions

- 회원가입에는 로그인 아이디와 비밀번호만 필요하다(이메일 인증·프로필 필드·약관 동의는 이번 범위 밖, 필요 시 후속 명세).
- 비밀번호 최소 길이 8자를 기본 정책으로 가정한다. 운영 정책이 다르면 이 값을 조정한다.
- 계정 생성 도메인 로직은 이미 존재한다(부트스트랩 어드민이 사용 중). 이 기능은 그 로직에 **공개 진입점**을 추가하는 것이며, 도메인 규칙을 새로 만들지 않는다.
- 회원가입 경로는 게이트웨이 인증 화이트리스트에 포함되어야 한다(공개 접근).
